# Project rules

- Product analytics uses a central consent-gated PostHog adapter in each client, with explicit semantic events, normalized paths and shared event names; identity uses only authenticated account IDs and resets on account changes. Why: comparable funnels without capturing credentials, private text, OAuth URLs, video surfaces or duplicate purchase attribution. Session replay, automatic text capture and advertising use remain disabled.

- Two clients, one product: `mobile/` (Flutter) is the shipped Android app; the root TanStack app is its interactive prototype rendered in a phone frame. Every UI or rule change lands in both, Flutter first. Why: the user previews on web but ships the APK.
- Founder visibility reads public read-only `onboarding_settings`, refreshed at startup/entry with a cached offline fallback; only privileged tools edit it. Trial preparation warms data, notes, poster and API bootstrap, never hidden players or downloaded clips. Why: remote presentation control without private-data access or extra decoder surfaces.
- Business rules live only in `src/lib/logic.ts` and `mobile/lib/logic/logic.dart`, kept 1:1 with mirrored tests (`src/lib/logic.test.ts`, `mobile/test/logic_test.dart`) asserting identical values. Why: the two clients must behave the same.
- Design tokens are defined in `src/styles.css` and mirrored in `mobile/lib/theme/tokens.dart`; components use tokens only. Why: one visual language across clients.
- Clip content is generated by `scripts/content/*` into `public/data/` and copied to `mobile/assets/data/`; never hand-edit the JSON. Why: the pipeline is cached and re-runnable.
- Explanation exports use `runtimeNotes` to keep only compact learner-facing word/line fields; source-cache signatures remain for validation, and `pack-notes.ts` can repack existing content without retokenizing it. Why: build metadata and formatting must not inflate either client's bundled data.
- Invalid source windows are excluded through scripts/content/excluded-clips.json (and embed-blocked videos through blocklist.txt), filled by `scripts/content/verify_library.py` from real official-player durations; both players also check loaded source duration. Why: AI-generated timestamps can refer to segments that do not exist.
- Dictionary matching in build.ts is part-of-speech aware (grammar words never take a kanji noun's entry) and JLPT levels match Waller rows by id and spelling plus `jlpt-fixes.json`; guarded by `src/lib/content-data.test.ts`. Why: の showed as 野 "field" and basic greetings showed N3–N1.
- Videos play only through YouTube's official embedded player (IFrame API on web, youtube_player_iframe on Flutter), never downloaded, re-hosted or audio-extracted, never covered by overlays; show channel attribution and a Watch on YouTube link. Why: YouTube API terms.
- Feed players exist only for the active clip and the next one (`warm`: loaded and cued, never playing or reporting playback); trial previews and stand-alone players stay single. Pause before the player is ready is queued, never sent. Why: faster swipes without extra video surfaces or crashes on early commands; YouTube's embed ignores quality requests, so startup speed comes from warming, not resolution.
- Feed loop/replay mechanics use mirrored PlaybackLoopGuard helpers; never correct early startup timestamps with repeated seeks or unlock seeks on a fixed timer. Why: YouTube reports zero/keyframes and stale positions while asynchronous seeks buffer, causing restart storms.
- Learner state is one JSON document (`mimi-state-v1`) stored locally and, when signed in, in `public.learner_state` (owner-only RLS), merged with `mergeState`; its `owner` scopes local progress to one account (`localStateFor`), so another account starts clean on that device. Why: offline-first multi-device sync without leaking one learner's progress into another account.
- Web app shell renders children only after hydration (AppFrame), so persisted state never causes SSR mismatches. Why: state lives in localStorage.
- Flutter purchases go through RevenueCat (`mobile/lib/services/billing.dart`, entitlement `premium`, offering `default`); `paywall.ts`/`paywall.dart` hold fallback prices that live store prices replace. The web prototype stays simulated. Why: one subscription backend for App Store and Play.
- Learning is centrally gated by mirrored subscriptionAccess/learningPath rules; native launch requires store verification, expiry revokes access, purchases are linked to the authenticated RevenueCat ID, and Ask verifies that ID's live Premium entitlement server-side. Why: saved flags or signed-in accounts alone must never unlock expired subscriptions.
- Direct-download APKs are split by ABI (arm64-v8a, armeabi-v7a, x86_64), size-reported in CI, and emulator E2E selects the x86_64 artifact; Play delivery stays AAB. Why: avoid bundling three runtimes on every phone without enabling unsafe R8 shrinking.
- APKs are built by GitHub Actions only after `flutter analyze` and `flutter test` pass; a second job installs the release APK on an Android emulator and runs `mobile/integration_test/` via `.github/scripts/e2e.sh`, saving screenshots + logcat. Why: failure is not an option for the shipped build.
- Release APKs are signed with one fixed key held only in GitHub Actions secrets (`ANDROID_KEYSTORE_*`, read via `KIZUKI_KEYSTORE*` env in `mobile/android/app/build.gradle.kts`); never commit a keystore. Why: phones refuse to install an update signed with a different key, and the repo is public.
- Android release builds keep R8 shrinking off (`mobile/android/app/build.gradle.kts`). Why: JNI-based plugins (shared_preferences) lose methods when shrunk and the app opens blank.
- The AI tutor (Ask Kizuki) runs only in the web app's server route `src/routes/api/public/ask.ts`, which requires a signed-in user's access token; both clients post the same AI SDK UI-message body, and the Android app calls the published origin (`AppConfig.apiOrigin`). Why: the AI key stays server-side and there is one tutor prompt.
- The web dev server ignores `mobile/**` (vite.config.ts). Why: Flutter build/test output otherwise reloads the preview mid-session.
- Word levels (1–4, Known, Ignored) are derived from the saved word's status + SRS card (`wordLevel`), never stored separately; picking a level reschedules the card (`withWordLevel`). Why: one source of truth, so reviews, Vocab counts and underlines can never disagree.
- Review answer cards show text context first and mount the official video player only in an explicitly opened sheet; familiarity controls group existing learning levels without resetting an already-learning card. Why: reviews stay focused and existing scheduling survives presentation simplification.
- Welcome-tour steps live in `src/lib/tour.ts` / `mobile/lib/data/tour.dart`; spotlight targets are `data-tour` attributes on web and `TourTargets` keys on Flutter, set only on the feed's active clip. Why: one tour definition per client, targets never point at off-screen clips.
- Ask Kizuki tour opens the real contextual sheet with an explicitly labelled local context/gloss example, never sending a question; tour sheets reserve the top area for compact tips while normal sheets retain their height; the tour closes the tutor/word sheets itself (web `closeSignal`, Flutter root-navigator pop) and moves on before their close events arrive, and a hand-closed card skips the remaining card steps. Why: onboarding must teach the tutor without spending a question, and learners must never be told to dismiss sheets or get stuck.
- Tour spotlights use only the visible part of a target (clipped to its scroll viewport) and the last step navigates back to the feed. Why: scrolled-away words otherwise lit the video, and ending on a flashcard stranded new users.
- Learner-facing schedule text uses `formatWhen` (plain words); compact `formatInterval` codes never appear on review buttons or word sheets. Why: "1m / 10m" confused learners.
- Flutter sheets (`showMimiSheet`) open on the root navigator, above the tab shell. Why: the web Sheet layers over the TabBar; inside the shell the floating tab bar covered cards and took their taps.

- Trial phone previews reuse the home ClipView and feed pager; only the settled clip creates a player, with no simulated transcript animations or geometry callbacks. Replace the founder route before opening trial to release its native video decoder. Why: real feed parity without retaining multiple video surfaces during onboarding.
- The first clips come from the curated starter list (`scripts/content/pick_starter.py` → content.json `starter`, showcase first) through the mirrored `starterFeedOrder` rule: same order for everyone in the onboarding preview, then in the home feed until watched or the watch limit, with a level guard for advanced learners; `rankFeed` stays the personal ranker. Why: one strong first impression without losing personal recommendations afterwards.
- Founder video uses one captioned master bundled in Flutter and registered as an asset pointer on web; player uses contain framing and app captions only on failure. Why: identical timing without doubled or cropped subtitles.
- Meta SDK (facebook_app_events, `mobile/lib/services/attribution.dart`) logs only install/open + onboarding; trial/purchase/renewal reach Meta via RevenueCat's server-side Meta CAPI integration, and the app passes the FB anonymous ID + device IDs to RevenueCat. Why: one source per event, no double counting.
- Store listing text lives in `store/listing.json` and store images in `store/screenshots/` + `store/play/`; `scripts/stores/push_listing.py` pushes both stores and `scripts/stores/screenshots/` re-renders the images from the running prototype. Why: one re-runnable source instead of hand edits in two consoles.
- Help messages are inserted into `public.support_messages` (insert-only RLS for anon + signed-in, no client reads); limits come from `supportMessageError` in both logic files. Why: there is no support inbox yet, and customers are never emailed automatically.
- Privacy Policy and Terms copy lives only in `src/lib/legal.ts`; `mobile/lib/data/legal.dart` is generated from it (`bun scripts/legal/gen_legal_dart.ts`) and `src/lib/legal.test.ts` fails on drift. Why: store reviewers read the web URL and the in-app page, which must say the same thing.
- Pinned-footer screens (onboarding steps, paywall) scroll their content inside a bottom-fading area (`scroll-fade` utility / `FadedScroll`) with the primary button outside it. Why: small phones and large system text must never push the main button or price off screen.

- Successful checkout/restore sets a local persisted purchase-account gate; only verified account completion clears it, and cloud merge never overrides it. Both clients block learning surfaces while pending. Why: payment must not be followed by a skippable or lost login step.
- Owner-only public.profiles stores identity display fields and learning preferences alongside learner_state; auth signup creates the row and sync updates it. Why: account profiles remain available across devices without an onboarding name prompt.
- Haptics go only through the semantic kinds in `src/lib/haptics.ts` / `mobile/lib/services/haptics.dart` (tap, select, tick, light, success, celebrate, error), gated by the persisted `settings.haptics` toggle; mascot/splash motion uses the mirrored curves in `mascot-motion.ts` / `mascot_motion.dart` and freezes under reduced motion. Why: both clients feel identical, and users can turn vibration off in one place.
- Phones use native Google/Apple signInWithIdToken only (mirrored signInProviders/signInMethod); failures stay in-app, never open a browser. Legacy incoming hand-offs remain readable; web retains browser OAuth. Why: preserve the native journey; verify backend audiences separately.
- Optional analytics starts only after explicit Settings opt-in; no launch consent overlay. Why: first use must not be blocked or silently enable tracking.
